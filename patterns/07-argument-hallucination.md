# Argument hallucination

The agent calls a tool with arguments that are not present in any prior context. Customer IDs invented, file paths made up, parameter values guessed.

## What it looks like

User asks: "show me the order history for customer Alex"

Agent calls `get_orders(customer_id="C-A47291")` despite never having seen that ID. The ID may even be plausible-looking; it just is not real.

Tool returns "customer not found"; agent often loops trying variations (see [tool-loop](01-tool-loop.md)).

## Why it happens

- The tool requires an ID but the agent only has a name
- The model fills in missing arguments with plausible-looking values rather than asking
- Training bias toward producing complete-looking tool calls
- No upstream tool was used to look up the actual ID first

## Detection signals

Easy to detect for some argument types:

- ID arguments that do not match a regex of valid IDs
- IDs that no upstream tool returned in this trace
- Arguments that contain placeholder patterns ("example.com", "test", "foo")
- Arguments that look templated ("USER_123" exactly when the system uses "U-487291" format)

Run these checks before executing the tool call. Catch the hallucination at validation time rather than at execution.

## Mitigations

### Required lookup pattern

For tools that take entity IDs, document a lookup pattern:

```
get_orders(customer_id):
  - customer_id must come from a prior find_customer call
  - to find a customer by name, email, or other identifier, use find_customer first
```

Then in the system prompt: "Do not provide ID arguments unless they appear in a prior tool result. If you need an ID, look it up with the appropriate find_* tool first."

### Argument schema validation

Define schemas for argument values:

```yaml
customer_id:
  type: string
  pattern: ^C-[0-9]{6}$
  description: Customer ID starting with C- followed by 6 digits
```

Reject calls that do not match the pattern. The error message should tell the agent how to obtain a valid ID:

```
{"error": "customer_id must match pattern C-NNNNNN. Use find_customer to get a valid customer_id."}
```

### Provenance tracking

Track where each argument came from. If an argument did not come from a prior tool result and was not provided by the user, flag the call as potentially hallucinated.

This is an instrumentation effort but pays off; you can audit how often agents are making up values.

### Disallow free-form ID generation

For tools where this matters most (database lookups, file operations, financial transactions), reject any ID argument that has not appeared in the conversation history. Force the agent to retrieve before referring.

### Better error messages

When a hallucinated argument fails, the error should be specific enough that the agent corrects without looping:

```json
{
  "error": "no customer with id 'C-A47291'",
  "suggestion": "use find_customer(name='Alex') to look up the actual customer_id"
}
```

A vague "not found" invites the loop pattern. A specific error with a suggestion fixes the behavior.

## When invented arguments are correct

Some arguments are supposed to be invented:

- A new entity being created (a new customer, a new file)
- A unique request ID for idempotency
- A user-chosen value (a new password, a project name)

The distinction: lookups should never invent IDs; creates often must.

Tag your tools by intent:
- `read_*` tools: IDs must come from prior context
- `create_*` tools: new IDs are generated by the system, not provided by the agent
- `search_*` tools: parameters are queries, not IDs

## A note on URL hallucination

A specific case: agents hallucinate URLs. They construct what they think a documentation URL should look like (`https://example.com/docs/api/v2/auth`) and call a fetch tool with it.

This is especially common when the agent has training data for an old version of an API. The URL pattern from 2022 may not match the current site.

Mitigation: require URL arguments to come from search results or user input, not be constructed. Most fetch tools should be paired with a search tool that returns valid URLs.

## A note on file path hallucination

In coding agents, file paths are a major hallucination source. The agent assumes a project structure ("there is probably a `src/utils/` directory") and writes to a path that does not exist.

Mitigation: require a `list_directory` or `find_file` call before any write to a non-existent path. Or sandbox writes such that creating new paths is explicit and confirmed.
